What the pair shows:
  - fetch: rust is a constant-factor win, 1.26-1.35x at every row count.
  - py-alloc is IDENTICAL (346 B/row) in both builds, ~10x the ~30 B the values themselves
    occupy — because both builds materialize rows as Python dicts of boxed values. The codec
    is not where the memory lives; the representation is.
  - gc pressure identical (+147 collections at 100k rows) for the same reason.
  - concurrency: rust shifts the whole latency curve down ~20-25% but the shape is unchanged —
    p50 roughly doubles with each doubling of workers in both builds (one shared box, GIL-held
    decode + server contention). The codec swap buys a prefactor, not a different curve.
  - conclusion for the storyline: "Python leaves little tuning room" is TRUE but not where the
    draft claimed. It is not data races and not fixable by a faster codec: the binding cost is
    the PyObject representation itself (346 B/row, identical across builds). Changing the
    curve requires changing the representation — rows landing in a non-Python buffer (Arrow /
    native driver), which is exactly the deferred handle-arm experiment (beads AIsummit26-zda).
