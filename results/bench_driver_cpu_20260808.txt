driver CPU/efficiency benchmark — finbenchl1, neo4j driver 6.1.0, same box as DozerDB.
Client CPU = process user+sys (all threads). Server CPU = DozerDB container cgroup
(docker-…scope/cpu.stat) delta, charged per fetch/call. ivcs = involuntary context switches.
client-util in the concurrency stage is measured against ONE core on purpose: with the GIL,
exceeding 100% is only possible while decode runs outside the interpreter, so it gauges
GIL escape.

What the hardware counters add to the story:

1. The fetch is CLIENT-CPU-BOUND. Single-threaded util is 92-95% in both builds — the wall
   time of pulling rows is almost entirely the client's own CPU, not waiting on the DB.

2. Consuming a row costs ~7x more CPU than producing it. At 100k rows the server spends
   ~290 ms of CPU while the pure-python client spends 2,085 ms and the rust client 1,551 ms.
   The expensive side of bridge 2 is the consumer.

3. The rust codec's real win is efficiency, not latency: 21 -> 15.5 us/row (-26% CPU per
   row) at identical server cost (~3.1/28.5/290 ms — so nothing was shifted to the server),
   and half the involuntary context switches (554 -> 261 at 100k).

4. The GIL ceiling is now measured, not asserted: with 8 workers the client process reaches
   only ~1.3 cores of utilization in both builds (131% pure, 136% rust) while cpu/call
   inflates 3x (42->121 ms pure) and involuntary switches grow ~linearly (+36 -> +1,619).
   Cores are available; the runtime cannot use them. A faster codec raises the ceiling a few
   points (134 -> 141% at w=4); only changing the row representation (rows landing outside
   Python objects — Arrow buffer / native driver) or multiprocess fan-out changes the curve.
   That is the quantitative case for the deferred handle-arm experiment (beads AIsummit26-zda).

note: rust w=8 server 15.3 ms/call is an outlier vs ~7 ms elsewhere; likely background
activity in the shared container during that window — re-measure before quoting it.
